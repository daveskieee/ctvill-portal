1. VERIFIED ISSUES AND FINAL INTEGRATION CORRECTIONS
================================================================================

[ISSUE 1: Worker Assignment and De-Assignment Atomic Transactions]
- Verified Defect: Manual worker assignment (`POST /:id/assign`) and unassignment (`DELETE /:id/assign/:projectId`) in `server/routes/workers.ts` performed series of separate non-transactional database updates. If an update failed midway (e.g. updating `commercial_projects` after updating `workers`), the database was left in an inconsistent state with mismatched headcounts and partial deployments.
- Applied Correction:
  1) Wrapped both assignment and de-assignment inside PostgreSQL transactions (`BEGIN` ... `COMMIT` / `ROLLBACK`).
  2) Synchronized `workers.assigned_project_id`, `project_worker_assignments` (active deployment), `contractors."activeProjectSite"`, and both target and donor `commercial_projects.assigned_contractor_ids` and `assigned_workers_count`.
  3) Enforced clean removal of prior active deployments across other projects, preventing duplicate deployments.

[ISSUE 2: Dual Project Authorization on Worker Transfers]
- Verified Defect: When an Engineer assigned a worker who was already deployed on Project A (donor) to Project B (target), authorization only checked if the Engineer had access to target Project B. An Engineer with access only to Project B could reallocate workers away from Project A without authorization over Project A.
- Applied Correction:
  1) Before modifying any database state, retrieved the worker's current active project (`donorProjectId`) from `workers.assigned_project_id` and `project_worker_assignments` with row-level locking (`FOR UPDATE`).
  2) If `donorProjectId` exists and differs from `targetProjectId`, verified the caller's authorization for BOTH projects (`checkUserProjectAccess(req.user, targetProjectId)` AND `checkUserProjectAccess(req.user, donorProjectId)`).
  3) If the Engineer lacks access to the donor project, the transaction is rolled back and rejected with HTTP 403 Forbidden without modifying any data.

[ISSUE 3: Transactional Payroll Disbursement and SQL Error Propagation]
- Verified Defect: In `server/routes/finance.ts` (`POST /api/payroll/disburse`), single and batch disbursements updated `payroll_runs`, `extended_payroll`, and `payroll_records` sequentially without an atomic transaction. Audit log creation swallowed errors via `.catch(() => {})`, and missing records still returned `{ success: true }`.
- Applied Correction:
  1) Wrapped both single and batch disbursements in explicit PostgreSQL transactions (`client.query('BEGIN')` ... `COMMIT` / `ROLLBACK`).
  2) Verified that target payroll runs (`PAY-...`), extended payroll items (`EP-...`), or legacy records exist before updating. Non-existent IDs return HTTP 404 with rollback.
  3) Inserted audit logs into `process_audit_logs` inside the same database transaction without swallowing SQL errors.
  4) Any SQL error rolls back all updates and returns HTTP 500 with descriptive error details, guaranteeing zero partial writes or false success reporting.

[ISSUE 4: Financial Reporting — Distinguishing Approved vs Paid Expenses]
- Verified Defect: In `server/routes/projects.ts`, `laborExpenses` and `subcontractorExpenses` combined approved/finalized unpaid expenses with already disbursed/paid expenses into a single figure, preventing finance controllers from distinguishing committed payables from disbursed cash outflows.
- Applied Correction:
  1) Separated aggregation in `server/routes/projects.ts`:
     - `paidLaborExpenses`: `SUM(total_gross)` from `payroll_runs` with `status = 'PAID'`.
     - `approvedLaborExpenses`: `SUM(total_gross)` from `payroll_runs` with `status = 'FINALIZED'`.
     - `paidSubcontractorExpenses`: `SUM(amount)` from `subcontractor_payables` with `status = 'PAID'`.
     - `approvedSubcontractorExpenses`: `SUM(amount)` from `subcontractor_payables` with `status = 'APPROVED'`.
     - `paidExpenses`: `paidLaborExpenses + paidSubcontractorExpenses`.
     - `approvedExpenses`: `approvedLaborExpenses + approvedSubcontractorExpenses`.
     - `totalExpenses`: `paidExpenses + approvedExpenses`.
  2) Preserved all existing payroll calculation formulas without double counting.
  3) Updated `ProjectProfile` in `src/types.ts` and `src/components/ProjectProfileHub.tsx` to clearly display both "Disbursed (Paid) Expenses" and "Approved/Pending" commitments.

[ISSUE 5: Gantt / Kanban Mutual Reconciliation and Payroll Uniqueness]
- Verified Defect: If a task's progress was updated to 1.0 via Gantt or API while passing a conflicting status, or if status was changed to `COMPLETED` with partial progress, the views could drift. Additionally, `server/routes/payroll.ts` lacked a check preventing re-finalization of already paid cycles, and `extended_payroll` item ID generation relied on an ambiguous 6-character suffix.
- Applied Correction:
  1) Enforced mutual reconciliation in `server/routes/projects.ts` and `server/routes/gantt.ts`:
     - When `status === 'COMPLETED'`, progress is reconciled to 1.0.
     - When `progress >= 1.0`, status is reconciled to `COMPLETED`.
     - When `progress < 1.0` and status is `COMPLETED`, status resets to `IN_PROGRESS`.
  2) In `server/routes/payroll.ts` (`POST /api/payroll/finalize`), added a guard rejecting re-finalization of an already `PAID` cycle with HTTP 400.
  3) Generated globally unique `extended_payroll` IDs using full run ID and worker ID (`EP-${runId.replace(/^PAY-/, '')}-${item.workerId}`).
