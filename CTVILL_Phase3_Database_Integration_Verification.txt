1. CONFIRMED INTEGRATION ISSUES AND APPLIED FIXES
================================================================================

[ISSUE 1: AI Workforce Recommendation Approval Disconnect]
- Problem: In `server/routes/workforce.ts` (`POST /api/labor-allocations/apply-ai-rec`), approving an AI recommendation updated the `contractors` table and `commercial_projects.assigned_contractor_ids`, but failed to synchronize the worker's operational records in `workers.assigned_project_id` and `project_worker_assignments`. As a result, the daily muster roll, timekeeping roster, and attendance logs did not reflect the AI-reallocated worker, leaving the worker on the donor project roster or causing conflicting records.
- Fix: Enhanced `/api/labor-allocations/apply-ai-rec` to:
  1) Update `workers.assigned_project_id = targetProj.id` and status to 'Active'.
  2) Remove conflicting active assignments in `project_worker_assignments` for any other projects.
  3) Upsert an active record into `project_worker_assignments` for `targetProj.id`.
  4) Emit SSE events via `broadcastChange` for `workers`, `contractors`, `projectWorkerAssignments`, `attendance`, `projects`, and `auditLogs`.

[ISSUE 2: Worker Assignment & De-assignment Inconsistencies]
- Problem: In `server/routes/workers.ts` (`POST /:id/assign` and `DELETE /:id/assign/:projectId`), project matching was strictly by UUID. If a client sent a project name (e.g. "NexBridge Software Hub"), the assignment failed or threw an FK constraint error. Furthermore, assigning a worker to a new project did not clean up their previous active project assignment in `project_worker_assignments`, leading to duplicate active deployments and corrupted manpower counts.
- Fix: 
  1) Safely resolved project IDs by either UUID or name (`SELECT id, name FROM commercial_projects WHERE id = $1 OR LOWER(name) = LOWER($1)`).
  2) Automatically terminated previous assignments in `project_worker_assignments` before inserting the new one.
  3) Synchronized `contractors."activeProjectSite"`, `workers.assigned_project_id`, `commercial_projects.assigned_contractor_ids`, and `assigned_workers_count`.
  4) On de-assignment, cleared `workers.assigned_project_id` and `contractors."activeProjectSite"` and decremented `assigned_workers_count`.

[ISSUE 3: Project Management Progress and Financial Disconnect]
- Problem: In `server/routes/projects.ts`, creating or deleting a task (`POST /api/tasks`, `DELETE /api/tasks/:id`) did not recompute the project's overall progress percentage or `tasks_count`. Additionally, `GET /api/projects` returned static or zero financial expense metrics, meaning disbursed payroll runs and subcontractor payables (AP) did not reflect on the project card or project detail hub.
- Fix:
  1) In `POST /api/tasks` and `DELETE /api/tasks/:id`, recomputed `commercial_projects.tasks_count` and `progress_percentage = ROUND(AVG(progress) * 100)` and broadcasted `projects`.
  2) In `GET /api/projects`, aggregated real disbursed labor expenses from `payroll_runs` (`status IN ('PAID', 'Approved', 'Finalized')`) and subcontractor payables (`subcontractor_payables` where `status IN ('Approved', 'Paid')`), populating `laborExpenses`, `subcontractorExpenses`, and `totalExpenses` on each project record.
  3) Updated frontend `ProjectProfileHub.tsx` and `types.ts` to display actual live project expense rollups without fabricated figures.

[ISSUE 4: Gantt Chart and Kanban Bidirectional Synchronization]
- Problem: In `server/routes/gantt.ts`, the Gantt task query omitted the task `status` enum (`TODO`, `IN_PROGRESS`, `COMPLETED`), and updates via Gantt only adjusted `progress` without synchronizing the Kanban `status` column (e.g., a task set to 100% in Gantt stayed `IN_PROGRESS` or `TODO` in Kanban).
- Fix:
  1) In `GET /:projectId/gantt`, added `status: t.status` to the mapped task response.
  2) In single-task update and batch transaction sync (`POST /sync` update action), bidirectionally aligned status and progress:
     - `progress >= 1.0` -> status becomes `COMPLETED`.
     - `progress < 1.0` and status is `COMPLETED` -> status resets to `IN_PROGRESS` (or `TODO` if progress is 0).
  3) Preserved Critical Path Method (CPM) calculations and predecessor dependency lag logic intact.

[ISSUE 5: Attendance Project Name vs UUID Resolution]
- Problem: In `server/routes/attendance.ts`, `GET /` and `POST /` accepted `projectId` query or body parameters, but certain frontend views and legacy clients passed project names. When a name was passed, queries returned empty sets or insertion failed foreign key validation against `commercial_projects.id`.
- Fix: Added safe project resolution at route ingress (`SELECT id FROM commercial_projects WHERE id = $1 OR LOWER(name) = LOWER($1)`). If resolved, queries and roster lookups use the canonical PostgreSQL UUID.

[ISSUE 6: Payroll Finalization and Disbursal Synchronization]
- Problem: In `server/routes/payroll.ts` (`POST /api/payroll/finalize`), finalizing a payroll run created records in `payroll_runs`, but did not populate the unified `extended_payroll` table used for cross-project financial reporting and disbursal tracking. In `server/routes/finance.ts`, disbursing a payroll run updated `extended_payroll` but didn't synchronize with `payroll_runs` status.
- Fix:
  1) In `POST /api/payroll/finalize`, inserted finalized worker payroll line items into `extended_payroll` with status `'Approved'`, capturing regular hours, overtime hours, gross pay, deductions, and net pay.
  2) In `POST /api/payroll/disburse` (`finance.ts`), synchronized both single-run and batch disbursals across `payroll_runs` (`status = 'PAID'`) and `extended_payroll` (`status = 'Disbursed'`), emitting real-time events for both modules.

2. DATABASE RELATIONSHIP AND DATA-FLOW CHANGES
================================================================================

A. Dual Worker Representation Synchronized:
   - Entity 1: `contractors` (directory/roster entity; fields: `id`, `name`, `trade`, `"activeProjectSite"`)
   - Entity 2: `workers` (operational muster roll entity; fields: `id`, `name`, `trade`, `assigned_project_id`, `status`)
   - Bridge Table: `project_worker_assignments` (fields: `id`, `project_id`, `worker_id`, `assigned_at`, `status`)
   - Data Flow: Any assignment change via `/api/workers/:id/assign`, `/api/workers/:id/assign/:projectId`, or `/api/labor-allocations/apply-ai-rec` updates all three tables inside atomic transactions or coordinated queries.

B. Project Task & Progress Rollup:
   - `commercial_projects.tasks_count` = `COUNT(project_tasks.id)`
   - `commercial_projects.progress_percentage` = `ROUND(AVG(project_tasks.progress) * 100)`
   - Triggers: Emitted automatically on task creation, task update, and task deletion.

C. Financial Labor & AP Aggregation:
   - `commercial_projects.laborExpenses` = `SUM(payroll_runs.total_net_pay)` where `status IN ('PAID', 'Approved', 'Finalized')`
   - `commercial_projects.subcontractorExpenses` = `SUM(subcontractor_payables.amount)` where `status IN ('Approved', 'Paid')`
   - `commercial_projects.totalExpenses` = `laborExpenses + subcontractorExpenses`
   - Data Flow: Calculated at API ingress (`GET /api/projects`) and dynamically displayed in `ProjectProfileHub`.

D. Gantt / Kanban Bidirectional State Flow:
   - Gantt `progress` [0.0 - 1.0] <==> Kanban `status` ['TODO', 'IN_PROGRESS', 'COMPLETED']
   - `progress >= 1.0` <==> `status = 'COMPLETED'`
   - `progress > 0 && progress < 1.0` <==> `status = 'IN_PROGRESS'`
   - `progress == 0` <==> `status = 'TODO'`
